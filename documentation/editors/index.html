Editors

pyk includes a language server, pyk lsp, and a debugger, pyk dap. An editor starts them and talks to them over the Language Server Protocol (LSP) and the Debug Adapter Protocol (DAP). Both are part of pyk, so there is nothing else to install: an editor only needs to know how to start them. Each editor’s section below sets up both.

The server gives:

  • Diagnostics: the first error in a file, from lexing, parsing, the module system, names, types or mutability. An error in an imported module is shown at the import that reaches it.
  • Hover: the type of the expression, binding, parameter or definition under the cursor, and for a name, the ## comment above its definition. Types are inferred where a function is called, so inside a function nothing calls, hover says so instead; while the program has a type error, it says that.
  • Go to definition: where a name is bound, in the same file, in a module it imports, or in the standard library.
  • Outline (document symbols): the defs, the top-level bindings and the imports.
  • Completion: keywords, builtins, the names in scope, and after m. the names that module m exports.
  • Signature help: while a call is typed, the function’s parameters with their types, the one being written marked, and what its ## comment says of each. A named argument marks its parameter.
  • References and highlights: every place a name is written, in the file and in the modules of the program.
  • Rename: a binding and every use of it renamed together. A rename that would make a use mean another binding is refused, and so is one of a name the standard library defines.
  • Inlay hints: the types the checker inferred, shown after each binding and parameter written without one, and after a def that does not say what it returns.
  • Folding: blocks, runs of comment lines, and the imports.
  • Semantic highlighting: functions, parameters, variables (a var apart from an = binding), modules, types, constructors and fields.
  • Quick fixes: + for the ++ and ^ for the ** Pyking no longer has, and for an & on Bools and the like, the use mutation line a var needs, a name in scope for a misspelt one, and an annotation changed to the type of the value.

Each document is checked as a program, together with the modules it imports. A module that is open in the editor is read from the editor, so an unsaved change is seen by every file that imports it.

Options and settings

  • --stdio uses standard input and output. It is the only transport and the default; it is accepted because some editors always pass it.
  • -L DIR / --lib-path DIR, and the environment variable PYKING_LIB_PATH, add library directories, as for pyk.
  • --log FILE appends every message in and out, and any internal error, to FILE. Use it when an editor’s setup does not work: standard output carries only the protocol, and editors often hide standard error.

An editor can send two settings, as initializationOptions or as the pyking section of its workspace configuration:

settingdefaultmeaning
libPath[]more library directories, searched after -L
diagnostics"change""change": check as you type, once typing pauses; "save": check only when a file is opened or saved

The debugger

pyk dap runs a program with the interpreter, as pyk <file> does, and lets the editor set breakpoints, step through the program, and show the calls in progress, their variables, and the value of an expression where the program stopped. It speaks DAP on standard input and output; --stdio and --log are as for pyk lsp. The editor’s launch request says what to run:

argumentdefaultmeaning
programthe Pyking file to run
args[]the program’s own arguments, what sys.args() answers
stdina file the program reads as its standard input; without one it reads nothing
cwdthe directory the program runs in
stopOnEntryfalsestop at the first statement
justMyCodetruestep over the code of the standard library and of -L libraries
libPath[]more library directories, searched after -L
releasefalsedebug the program as --release compiles it, every debug() removed

A breakpoint stops at the first statement starting on its line or after it, and may have a condition (a Bool expression), a hit count (3 for the third time only, >= 3, % 2) or a log message, which is printed instead of stopping, with each {expression} in it replaced by its value. A runtime error stops the program where it happens unless the editor turns off the Runtime errors breakpoint. An expression evaluated where the program stopped — a watch, the debug console, a hover — is type-checked against the names in scope there. Only a var can be given a new value. A tinyweb program’s callbacks are debugged too: a breakpoint in one stops when its event arrives.

The program’s standard output and its debug lines arrive in the editor’s debug console, as standard output and standard error.

The examples below assume pyk is on your PATH. If it is not, write its full path in place of pyk.

Zed

There is no Zed extension for Pyking yet. Zed requires an extension to add a language, so a server cannot be configured on its own. An extension is planned.

When it does not work

  • Run pyk --version in a terminal. If it fails, pyk is not on the PATH the editor sees; give the editor the full path instead.
  • Add --log FILE to the command, for example pyk lsp --log /tmp/pyk-lsp.log, open a .pyk file, and read the log. If the file is empty, the editor did not start the server. pyk dap --log FILE does the same for the debugger.
