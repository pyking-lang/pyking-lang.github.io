Notebook

A Pyking notebook is a Markdown file. Its text is shown as a page, and each ```pyking block in it is a cell: a program the reader can edit and run in the browser. Other blocks turn the notebook into an assignment, with tasks a student solves in the page, quizzes, and points.

Notebooks are meant for teaching and for exploring. The file is the notebook: you write it in any editor, keep it in git, and it still reads well in any Markdown viewer.

As in the playground, the cells run in the browser with the Pyking interpreter. Nothing runs on a server; pyk only hands the browser the files.

Running a notebook

CommandWhat it does
pyk notebook book.mdserves the notebook and prints a link to open
pyk notebook book.md --mode teachershows every solution, test and answer, and the problems test mode finds
pyk notebook book.md --mode testserves nothing: checks the notebook and prints each problem
pyk notebook book.md --port 8100serves it on port 8100
pyk notebook book.jsonthe same, for a notebook in its JSON form

--mode student is the default.

pyk notebook watches the file. Save a change in your editor and the page reloads, scrolled where it was. A student’s progress is kept over the reload, except for a task or quiz whose block you changed.

Links to other .md files beside the notebook open as notebooks too, and images load from the notebook’s own directory.

Using a notebook

▶ beside a cellruns it
Shift+Enter in a cell, or in its stdin or args fieldruns it and moves to the next cell
Ctrl+Enter (Cmd+Enter on a Mac)runs it and stays
Escapeleaves the cell
■ while it runsstops it
reset, shown once a cell is editedputs back the code the notebook has

Cells run one at a time. [n] beside a cell counts runs across the page, as in Jupyter, and [*] marks a cell that is waiting or running. What a cell prints appears under it as it is printed. An error is shown under the cell, in the words pyk uses, and underlined in the code.

Edits to a cell last until the page is reloaded; the file is never changed. Every cell, and every input and output box, has a copy button in its top right corner, shown while the pointer is over it.

Prose

Everything outside the notebook’s blocks is Markdown, as on GitHub: headings, emphasis, inline code, links, images, lists and task lists, tables, quotes, footnotes, rules and HTML. A fenced block in another language is shown highlighted. A front matter title: names the page; without it, the first # heading does. The headings, down to ###, are listed in a contents sidebar.

The callouts are [!NOTE], [!TIP], [!IMPORTANT], [!WARNING] and [!CAUTION]. Math is typeset with KaTeX: $…$ inline, and $$…$$ or a ```math block for display. $5 and $6 stays text.

A ```pyking block (or ```pyk) is a cell. A word after pyking changes it:

Each cell is a whole program, run on its own. A name defined in one cell is not seen in the next, and a cell that uses var or := needs its own use mutation line:

A cell may import the standard library.

A cell’s input

A cell whose program reads standard input (io.read_line, io.read, io.is_eof) shows a stdin field above its code, and one that reads sys.args() shows an args field. The reader types into them. The notebook can fill them in, on the cell’s header:

or in a ```stdin or ```args block right before the cell, which is not shown on its own:

A value on a header is a word or a quoted string, in which \n is a new line. Arguments are split at spaces, with quotes keeping a space inside one. What the notebook gives is only where the fields start: the reader can change it.

What a cell prints

A ```stdout block after a cell says what the cell prints, and a ```stderr block what it writes with debug. Test mode checks that the cell does print that. They are hidden unless they say visible = true; a visible one reads as if the cell had already run, until the reader runs it. A ```stdin block between the cell and its output is the input the output was made from.

A cell that checks but may be wrong shows its warnings, such as a name never used, above what it prints. pyk notebook -Wall book.md, or any other of pyk’s -W flags, says which warnings are shown.

tinyweb in a cell

A cell that uses tinyweb shows its page under the cell: canvases, buttons, sliders and sound. The program goes on running after its last line, so a click calls back the function it was given, until the cell runs again, another cell runs, or ■ is pressed.

An ```events block after such a cell is what its page is sent when test mode runs it: one event a line, as under Tests below.

Assignments

A notebook becomes an assignment with tasks the student solves in the page, quizzes they answer, and points that add up to a pass. A bar at the top and the end of the page says how many are solved, the points, and whether they pass. Its start over forgets every answer.

A student’s progress, their code, their choices, the attempts used and the points, is kept in their browser, per notebook.

The rules

The rules are shown in a box at the top, with max and pass. A notebook has at most one rules block. max must be the sum of the points of every task and quiz, and a student passes with pass points or more.

Tasks and practices

The prose before a ```pyking task block states the task. The block holds the code the student starts from, which must run. After it come an optional solution and the tests:

That task has two tests: 4, which the student can see with what it should print, and -3, which is hidden.

Submit, under the task, runs the student’s code on every test. Where there is a solution, it runs too, on the same input, and the two must print the same, draw the same with tinyweb, and end with the same exit status. Without a solution, the student’s output must match the stdout and stderr blocks. Spaces at the end of a line and blank lines at the end do not count. Each run may take ten seconds. Running the cell with ▶ is free; only a failed Submit uses an attempt.

When a Submit fails, the red box says why, and See result diff shows the first test that differed: its input, the two outputs side by side, and, for a tinyweb program, what each one drew. A solved task turns green.

Tests

A test is a ```stdin block, an ```events block, a ```stdout block or a ```stderr block, or several of them in that order. A test with no stdin block runs on the task’s own input. Each takes visible = true to be shown to the student.

Here every two lines of the stdin block are a test of their own, each compared with what the solution prints.

Loosening the comparison

Four blocks under a task let an answer differ from what is expected in ways that do not matter. Each applies to what is printed, what debug writes, and the tinyweb log. Their lines are patterns; in the last three, * stands for any text.

BlockLets an answer
```diff-allowedhave numbers that differ by at most [+/-N]
```optional-lastend with lines the other side does not have
```any-orderwrite some lines in any order between given lines
```ignore-chars chars = "…"differ in the given characters on lines that match

With these, area = 12.57 matches area = 12.56636, a pause at the end of a beat may be left out, drums played on the same beat may come in any order, and point 1,2 matches point 1, 2.

Comparing only the start

A program that plays a beat forever never ends, so it cannot be compared whole. A ```compare-until block says how much is compared: each run stops after events lines of the tinyweb log that match its patterns.

Answering with git

A task with method = git is answered outside the page. The page still shows its code and its visible input, and ▶ runs the code, but in place of Submit it says “Please submit via your git account”. The answer is graded from the notebook’s tests with nbverify.

Limiting calls

max_calls limits how often an answer may write a name: here rect at most twice. Every place counts, outside comments and strings: rect(...), tw.rect(...) and def rect. The limit is shown as a badge, and an answer that breaks it is refused before it runs.

Examples

An ```example block shows what a task’s solution does with an input, usually in the prose before the task, so the reader sees what is asked before trying. Its text is the input. The page runs the solution on it and shows the input and what the solution printed, drew, or both. The solution’s code is not shown.

Quizzes

The question is the prose before a ```quiz block, or the text inside it before the first alternative. An alternative starts a line with * where the student picks one, or with [] where they may check any number. An ```answer block follows, with one entry per alternative, in order: -> for right, - for wrong, then the explanation, which may be empty.

A * quiz has exactly one right alternative:

Quiz headerMeansDefault
name, attempts, points, penaltyas for a tasknone, no limit, none, 0
available = trueonce the attempts are used up, the right answers are marked and every explanation shownfalse: only “failed”
one_point_correct = truea [] quiz gives a point for each right alternative checked, and none when more are checked than there are right ones; its points is the number of -> entriesfalse

A wrong Submit shows the explanation of each wrong alternative chosen, and for checkboxes says when a right one was left unchecked.

Student and teacher

--mode student, the default, shows a solution only where it is available and the student asks for it, a test only where it says visible = true, and no quiz answers.

--mode teacher shows every solution, test and answer. It also runs test mode’s checks in the page, and shows under each task, quiz, cell and the rules that they have no problems, in green, or what the problems are, in red. Use it while you write a notebook.

The answers are checked in the browser, so in both modes the whole file is sent to it. A student who reads the page’s source can find the solutions. For graded work, use nbverify.

Test mode

Test mode serves nothing. It reads the notebook as the page does, runs every program, and prints each problem as file:line: message. It exits with status 1 if there is any problem, and 0 otherwise, so a continuous integration job can run it on every notebook of a course. It needs node.

It checks that:

  • the blocks are where they belong, with valid headers: a solution after its task, an answer after its quiz with an entry per alternative, one -> in a * quiz, numbers where numbers belong, names valid and unique;
  • there is at most one rules block, and its max is the sum of the points and not less than pass;
  • every cell runs, every error cell is refused, and every task’s starting code runs;
  • each cell and each solution prints what the stdout and stderr blocks after it say, on each test’s input and events, and each solution keeps to its task’s max_calls;
  • a task without a solution has an output to compare an answer with;
  • each example names a task with a solution, and the solution runs on the example’s input.

A cell that uses var without its own use mutation line, for example, is reported here.

The JSON form

A notebook can also be written as JSON. Use it when a program, not a person, writes or reads notebooks, for example to generate a notebook from a question bank or to import one into another system.

CommandWhat it does
pyk notebook book.md --to-jsonwrites book.json beside it
pyk notebook book.json --to-markdownwrites book.md beside it
pyk notebook --json-schemawrites notebook.schema.json, the JSON Schema every notebook’s JSON follows

-o FILE names the file written, and -o - prints it. A file of the default name that is already there is not written over. --to-markdown gives back the same Markdown, byte for byte. pyk notebook book.json serves and tests the JSON as the Markdown it stands for.

Grading with nbverify

The answers a student submits in the page are checked by their own browser. For grades that count, nbverify.py grades a notebook’s tasks and quizzes on a server, for the ID2202 autograder. It is one Python 3 file, in a Pyking installation under tools/nbverify/, and needs pyk to make the tests.
